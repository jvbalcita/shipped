# In-app notifications — plain writes, no Laravel Notifications

In-app notifications v1 covers exactly five recipient-targeted triggers: someone follows you, cheers your project, reviews your project, comments on your project, or replies to your comment. They are written by a plain `NotificationRecorder` service (symmetric with the `ActivityRecorder` from ADR 0005) at the same observer hook points that feed the activity log — one event, two cheap writes, no queue. Laravel's Notification system is deliberately not used: it is a delivery channel abstraction whose value arrives with email/push, and the Weekly Digest feature (not this one) owns email. A plain writer keeps the migration trivial to adopt later.

Two guards live in the recorder so every hook shares them: self-actions never notify (cheering your own project, replying in your own thread), and one notification per event per recipient — dedupe on (user, type, actor, subject) — so re-cheers after a toggle and observer retries stay silent. Recipient sets are explicit and tiny: the project owner, the parent comment author, or the followed creator; there is no fan-out, and project follows notify nobody.

The surface is a bell in the app shell plus a private `/notifications` page. The unread count rides a shared Inertia prop re-evaluated on every request, so the badge refreshes on navigation without polling — correct for v1 traffic, and the seam to add an endpoint or poll later if staleness between navigations ever matters. Viewing the page marks the displayed rows read after their unread state has been captured for that render, and a mark-all-read action covers stragglers. Pagination is an id-desc cursor keyset: the cursor paginator can only carry points for real columns (a `read_at IS NULL` raw ordering breaks the generated WHERE clause), so unread rows are floated to the top of each page in PHP instead of SQL — honest at v1 row counts, and swappable for a real ordering column if the inbox ever grows.
