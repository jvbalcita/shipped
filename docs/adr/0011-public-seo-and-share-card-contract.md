# Make discoverable public records the canonical SEO surface

## Context

Shipped is a community showcase for projects launched on Laravel Cloud. Its public value comes from trustworthy records: a creator, a project, a published release, and current verification evidence. The application already has public routes for the home page, Discover, creators, projects, releases, and project Share Cards.

The current public shell has project-level Open Graph output, but metadata is not yet a complete contract across public pages. The application also has no dynamic sitemap, canonical URL policy, structured-data policy, or explicit distinction between the Discover browsing experience and indexable search surfaces.

Search engines can discover server-rendered metadata and links, but indexable URL count is not a product goal by itself. Query combinations, empty creator pages, stale verification states, and thin facet pages could make Shipped look less trustworthy while creating duplicate or low-value search surfaces. Share Cards have a related risk: they must reflect the same public record that a visitor sees, remain stable for crawlers, and never expose a private or stale project.

## Decision

### 1. Canonical public surfaces

The canonical SEO surface is limited to public records with durable user intent:

- Home
- The base Discover page
- A public Creator page when the creator has at least one discoverable Project
- A discoverable Project
- A published Release whose parent Project is discoverable

The canonical URL is the public route generated by Laravel's named route. A URL is not canonical merely because it is reachable; it must represent the preferred public route for that record.

### 2. Browsing and filtered URLs

Discover remains filterable for product use, but arbitrary filter, search, sort, and pagination combinations are not a programmatic SEO product.

Filtered Discover URLs use noindex,follow and are excluded from the sitemap. Their canonical target is the base Discover URL unless a future, separately approved hub has a materially different intent and unique content.

The initial scope does not create indexable pages for tags, pricing, locations, personas, comparison combinations, or other query facets.

### 3. Programmatic page gates

Future category hubs may be introduced only when a category has enough public supply and editorially distinct value. The minimum launch gate is:

- At least 8 discoverable Projects
- At least 3 represented Creators
- A unique introductory paragraph and useful internal links
- A meaningful reason for the page to exist beyond repeating a filter result
- A test proving empty and below-threshold categories are not indexable

The same gate applies to any future collection template. Quantity alone never justifies an indexable page.

### 4. Sitemap and robots

The sitemap contains only canonical, currently public URLs for Home, Discover, eligible Creator pages, discoverable Projects, and eligible published Releases. Private, unverified, stale, unfinished, or otherwise non-discoverable records are absent.

Robots exposes the sitemap URL and does not attempt to use disallow rules as a substitute for noindex. Query surfaces are controlled by page metadata and canonicalization.

### 5. Structured data

Structured data is added only when the record supplies accurate values:

- Home: Organization and WebSite identity where the fields are true
- Creator: ProfilePage only when the public page actually contains a creator profile and public work
- Creator, Project, and Release: BreadcrumbList where the breadcrumb is visible and stable
- Project: SoftwareApplication only when the product type, name, URL, description, and any optional fields are accurate

Structured data must describe visible page content, use the canonical URL as its stable identity, and never be used to manufacture unsupported ratings, prices, authorship, or verification claims.

### 6. Share Cards

Share Cards are deterministic server-rendered projections of public records. The existing 1200 by 630 SVG renderer remains the design source and should be extended through explicit variants rather than a user-editable card builder.

The first variants are:

- Site: Home or general Shipped identity
- Project: project name, category, creator, verification-aware context, and short tagline
- Release: release title, parent project, publication context, and creator

Creator cards are deferred until the public Creator page has a sufficiently complete and stable profile contract. A Creator card must not be added merely because a route exists.

Cards use only data that is already safe to show on the corresponding public page. A private, stale, or otherwise non-discoverable record does not receive an indexable or shareable card. The endpoint is cacheable and deterministic for the same public record state.

SVG remains the default delivery format while compatibility is tested. PNG or JPEG delivery is added only if a representative social crawler fails to render the SVG reliably. A raster fallback must use the same template and data contract; it must not become a second design system.

## Alternatives considered

### Index every Discover facet

Rejected. It would create many URLs without adding equivalent content, increase canonical ambiguity, and make thin or empty combinations look like first-class Shipped destinations.

### Build a generic blog, glossary, or comparison engine

Deferred. Those surfaces could be valuable later, but they would require a separate editorial and measurement loop. They are not necessary to make the existing public records crawlable and shareable.

### Use manually authored static images

Rejected for record cards. Manual assets drift from project data and cannot scale as Releases change. A deterministic template keeps the visible card aligned with the public record.

### Generate arbitrary HTML or AI-written card copy at request time

Rejected. Runtime variability harms cacheability, visual consistency, and privacy review. Share Cards should use bounded, record-backed text with predictable wrapping.

## Consequences

Positive consequences:

- Search engines receive a smaller set of stronger, understandable URLs.
- Verification and discoverability remain part of the public trust contract.
- The sitemap, page metadata, structured data, and Share Cards can share one visibility rule.
- The existing industrial/editorial SVG style can evolve without introducing an image-editing product.

Costs and trade-offs:

- Some valid browsing URLs will not be indexable.
- Category SEO requires waiting for real supply and editorial differentiation.
- SVG compatibility must be tested before deciding whether raster delivery is needed.
- A future Creator Share Card needs a deliberate profile-content decision rather than automatic template expansion.

## Rollout boundary

Implement the baseline metadata, canonical rules, sitemap, structured data, and Share Card variants first. Submit the sitemap and observe indexing, impressions, clicks, and query quality after public supply exists. Expand into category hubs only after the density and unique-value gate is met.

This decision does not authorize a keyword-stuffed content engine, generated tag pages, an analytics SDK, or an editable Share Card designer.
